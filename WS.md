# План внедрения WebSocket (iTick Forex)

Документ фиксирует план интеграции WS без изменения текущего кода до явного старта работ.

## Цели

- Убрать опрос по таймеру (`_monitoring_poll_loop` + `sleep`) в пользу потока событий по подписке.
- Оставить REST `fetch_candles` как резервный канал (fallback).
- Сохранить поведение «сигнал при смене состояния» (`monitor_prev_had_signal`).

## Справка по iTick

- Подключение: заголовок `token`, затем сообщения connect / auth / subscribe (см. [Forex WebSocket](https://docs.itick.org/websocket/forex)).
- URL кластеров (согласовано с REST-окружением проекта):
  - **DEV / free:** `wss://api-free.itick.org/forex`
  - **PROD:** `wss://api0.itick.org/forex`
- Подписка: `params` в формате `CODE$REGION` (например `EURUSD$GB`), поле `types` — канал (`quote`, `tick`, `depth`, `kline@N`).
- Heartbeat: сервер может разорвать соединение без `ping`/`pong` (~1 мин). Рекомендация: лёгкий keepalive на транспортном уровне (например раз в ≤30 с простоя исходящего трафика), не смешивать с торговой логикой.
- Лимиты: до 500 символов на соединение; при медленном чтении буфер на стороне сервера — риск разрыва.

## Маппинг таймфрейма

Внутренние `k_type` в боте **не совпадают** с номером периода в `kline@N` у iTick:

| Внутренний `k_type` | Смысл   | WS `types` (iTick) |
|--------------------|---------|---------------------|
| 1                  | 1 мин   | `kline@1`           |
| 2                  | 15 мин  | `kline@3`           |
| 3                  | 30 мин  | `kline@4`           |

Нужен явный словарь `KTYPE_TO_WS_TYPE` (или эквивалент), а не `kline@{k_type}`.

## Слои реализации

### 1. Транспорт (iTick WS)

Отдельный модуль/класс: connect → ожидание успешного connect → auth → `subscribe` → цикл чтения сообщений, разбор JSON, маршрутизация `tick` / `quote` / `depth` / `kline@*`.

- Обработка обрыва: reconnect + повторная подписка.
- Ping/pong — только как поддержание соединения.

### 2. Состояние свечей

- Накопление свечей по ключу времени открытия `t` (как сейчас список словарей из REST).
- На каждом событии kline обновлять соответствующую свечу; определение «бар закрыт» — по текущей логике (`is_candle_closed` / граница следующего бара), согласованно с `format_candles`.

### 3. Бизнес-логика

- Вынести или переиспользовать цепочку: сырые свечи → `format_candles` → `calculate_indicators` → `check_signal` (как в `main()`, но без обязательного HTTP при каждом тике).
- При появлении валидного закрытого контекста для последних баров — сравнить с `monitor_prev_had_signal` и при необходимости отправить уведомление в Telegram.

### 4. Связка с `telegram_bot.py`

- Заменить `_monitoring_poll_loop` на фоновую задачу, которая:
  - держит подписку на выбранную пару и `k_type`;
  - по событиям обновляет буфер и пересчитывает сигнал;
  - шлёт `bot.send_message` при фронте сигнала (как сейчас при `has_signal and not prev`).
- Синхронные части (`main()` / pandas / старый `requests`): вызывать из async через `asyncio.to_thread` или вынести чистый пересчёт без блокировки event loop.
- `_stop_monitoring_task`: отмена задачи + закрытие WS / отписка, очистка `user_data`.

Опционально: `asyncio.Queue` между потоком/воркером WS и корутиной бота, если WS-клиент синхронный.

### 5. Кнопка «Запросить данные»

- Предпочтительно: ответ из **кэша последнего пересчёта** (без лишнего REST).
- Если кэша нет или данные устарели: **fallback** на существующий `fetch_candles` + текущий `main()`.

### 6. `main.py` / `Itick`

- `fetch_candles` не удалять; новый метод получения свечей по WS — отдельно.
- В точках «один раз получить историю» можно: сначала WS-буфер / быстрый bootstrap, при ошибке — REST.

## Ожидаемое поведение для пользователя

- После закрытия свечи (по правилам проекта) сигнал может прийти **без** нажатия «Запросить данные»; возможна небольшая задержка от сети и момента пуша от iTick.
- «Запросить данные» остаётся для явного запроса текстового снимка индикатора в чат.

## Порядок внедрения (когда начнём менять код)

1. WS-клиент + маппинг URL и `k_type` → `kline@N`.
2. Метод/сервис накопления свечей + тест на одной паре.
3. Подключение к боту: замена poll-loop, stop/cancel.
4. Fallback REST и ручной запрос данных.
5. Прогон на DEV, затем PROD.
